# ADR 007: Destackifying the EVM Stack

```
status: accepted
project: jet
area:
  - compiler
  - llvm/ir
  - optimization
```

## Context

EVM bytecode is stack machine code. The original Jet compiler lowered almost every
stack operation to calls into runtime helpers such as `jet.stack.push.i256`,
`jet.stack.pop`, `jet.stack.dup`, and `jet.stack.swap`. This kept the stack as an
opaque array in `Context.stack`, preventing LLVM from reasoning about values across
instructions and preventing many standard optimizations.

To improve code quality, the compiler needs to represent the operand stack as LLVM
SSA values for as much of a contract as possible. This is the "destackifying"
work: turning stack traffic into value flow.

## Decision

Jet now has two stack backends selected per compilation through
`builder::env::Options::with_stack_mode`:

- `RuntimeStackBackend` keeps the original behavior of calling runtime helpers for
  push, pop, peek, dup, and swap.
- `SymbolicStackBackend` tracks EVM stack slots as LLVM `IntValue` values during IR
  construction and materializes them into `Context.stack` only at contract exits,
  jump failures, and planned stack fault exits.

`RuntimeStackBackend` is both the default and the automatic fallback when symbolic
planning exceeds its limits. Both backends emit the same opcode implementations
from `ops.rs`; only the stack abstraction changes.

## Detailed Design

### StackBackend Trait

The trait abstracts push, pop, peek, dup, swap, and materialization. Opcode
emitters in `ops.rs` use generic stack operations without knowing which backend is
active. This lets a single opcode implementation run in both modes.

### Symbolic Control-Flow Plan

Symbolic mode builds a control-flow plan before emitting IR. The plan is an abstract
interpretation over code blocks that tracks:

- current stack height;
- optional `known_u64` metadata for each slot, used for static jump targets and
  small literals;
- the block index reached by each successor edge.

The analysis starts at block 0 with an empty stack and runs to a fixed point. When
the same bytecode block is reachable with different stack heights, the planner
creates separate block variants so each variant has a single stable entry height.
Static `JUMP` and `JUMPI` targets use a `jumpdest_pc -> block_index` map built during
block discovery. Dynamic jump targets conservatively add edges to every known
`JUMPDEST` variant at the current height.

### Entry Phis and Joins

All entry phis for all planned block variants are created before any block body is
emitted. This lets backedges target a phi that already exists. When two incoming
states for the same block variant disagree on a known literal, that slot's metadata
is dropped to `None`, but the LLVM value is still merged by the phi.

### Planned Stack Fault Exits

Abstract stack faults along a statically reachable path do not abort compilation.
Instead, the planner marks the variant as faulting. Emission runs the instructions
before the fault for their side effects, trims the stack to the fault height,
materializes it, and returns `StackUnderflow` or `StackOverflow`. This matches the
runtime backend's checked helpers exactly and keeps the two backends differentially
testable.

### Fallback to Runtime Backend

Planning is bounded to a constant number of variants per block and a constant total
number of variants. If a contract exceeds either cap, the planner aborts and the
contract is compiled with `RuntimeStackBackend` into the same function. The fallback
is logged at info level. This is how runtime mode remains supported long term: it
is the safe fallback and the differential oracle, not a separate first-class mode.

## Rationale

### SSA Values Enable LLVM Optimizations

Once stack slots are LLVM values, LLVM can perform constant propagation, dead code
elimination, strength reduction, and target-specific instruction selection on EVM
operations. The opaque runtime stack blocked all of these.

### A Fallback Keeps Compilation Sound

Symbolic planning cannot bound every contract because EVM bytecode is unconstrained.
Automatic fallback means the JIT never rejects a contract for being too complex;
it simply uses the slower path.

### Shared Emitters Avoid Mode Drift

Because opcode implementations are generic over `StackBackend`, there is one list of
implemented opcodes and one set of semantics. The only mode-specific code is the
stack abstraction and jump dispatch helpers.

### Runtime Backend as Oracle

Every ROM test runs against both backends and asserts the same observable result.
This makes runtime mode a cheap differential oracle for symbolic correctness.

## Consequences

### Positive

- Better generated code: EVM values flow as LLVM SSA instead of through memory.
- Simpler opcode implementations: emitters do not manage stack indices.
- Differential testing: every test validates both backends against each other.
- Bounded risk: complex contracts fall back to the proven runtime path.

### Negative

- Complexity: the planner, variant system, and phi management add significant code
  to the compiler.
- Compile time: planning can grow with pathological bytecode; the caps prevent
  unbounded blowup but may force more contracts to the runtime path.
- Latent invariants: the planner's stack effects, the `SymbolicStack` operations, and
  the per-opcode emitters must agree on the semantics of every instruction.

### Mitigations

- `StackBackend` unifies opcode emission so semantics are not duplicated per mode.
- Debug assertions compare emitted block exit heights against the planned heights.
- A single rule extracts `known_u64` metadata for `PUSH` data for both the planner
  and the emitters.
- All ROM tests run in both modes.

## Future Work

- Make symbolic mode the default once the opcode surface is identical between modes.
- Constant-fold arithmetic to produce more static jump targets.
- Share dynamic jump switches between sites at the same height.
- Profile and tune the variant caps.
