# ADR 005: EVM Memory Expansion in the Runtime

```
status: accepted
project: jet
area:
  - runtime
  - memory-model
```

## Context

EVM memory is a byte-addressable, dynamically growing linear buffer. Every
operation that reads from or writes to memory must first ensure that the accessed
range exists. The expansion rules are:

- Memory starts empty (zero length, some initial capacity).
- Accessing any byte in the range `[offset, offset + size)` grows the accessible
  length to at least `offset + size`, rounded up to the next multiple of 32 bytes.
- A zero-size access is a no-op, even at very large offsets.
- Expansion is monotonic: the accessible length never shrinks during a single
  execution.

Jet stores EVM memory outside the `Context` struct using the pointer-based layout
described in ADR 002. This means the runtime, not LLVM generated code, owns the
allocation strategy and the safety checks that guard it.

## Decision

All memory growth is handled by a single runtime builtin, `jet_mem_expand`.
Every operation that touches memory calls it first with the raw byte offset and
byte size. Generated code checks the returned `i8` and branches to `ReturnCode::Invalid`
on any non-zero result.

`jet_mem_expand` implements the EVM rules directly:

1. If `size` is zero, return success immediately.
2. Compute `end_offset = offset + size` using `checked_add`; a `u32` overflow
   returns `ArithmeticOverflow`.
3. Round `end_offset` up to a multiple of `WORD_SIZE_BYTES` to get the required
   accessible length.
4. If the required length is already less than or equal to `memory_len`, return
   success.
5. If the required length exceeds `memory_cap`, allocate a new 32-byte aligned
   zeroed buffer, copy the existing bytes, free the old buffer, and update
   `memory_ptr` and `memory_cap`.
6. Set `memory_len` to the required length.

Only `Context::new`, `Context::Drop`, and `jet_mem_expand` may modify the memory
pointer, capacity, or accessible length.

## Rationale

### One Function for All Expansion

Centralizing expansion means there is exactly one place that interprets EVM
memory semantics, allocates new pages, and validates arithmetic. Opcode emitters
do not need to duplicate rounding, overflow checks, or allocation logic.

### Monotonic Length Simplifies Accessors

Because `memory_len` only grows, any code that has already expanded memory to a
certain length can rely on that length for the rest of the instruction. Helpers
like `Context::memory` and `Context::memory_mut` can return slices bounded by
`memory_len` without re-checking for every byte.

### Word Alignment Matches EVM Charging

EVM charges memory expansion per 32-byte word. Rounding the accessible length up
to the next word means the runtime length matches the gas model and avoids partial
word edge cases in generated code.

### u32 Bounds are Sufficient

The `u32` limit for offsets and sizes is justified separately in ADR 004. The
expansion function uses `u32` arithmetic with an explicit overflow check, so
attempting to expand past `u32::MAX` returns an error rather than wrapping.

## Implementation

### Runtime Function

```rust
pub unsafe extern "C" fn jet_mem_expand(ctx: *mut Context, offset: u32, size: u32) -> i8;
```

Return codes:

| Value | Meaning |
|------:|---------|
| `0`   | Success |
| `-1`  | Null context pointer |
| `-2`  | `offset + size` overflow |
| `-3`  | Allocation failure |

### Context Memory Fields

```rust
pub(crate) memory_ptr: *mut u8,
pub(crate) memory_len: u32,
pub(crate) memory_cap: u32,
```

`memory_ptr` is 32-byte aligned and initially allocated in `Context::new`.
`memory_cap` is the true allocation size. `memory_len` is the portion accessible
to EVM instructions.

### Allocation Strategy

The current implementation allocates exactly the required rounded length when
growing. A future improvement could over-allocate (for example, double the
capacity) to amortize reallocation costs, similar to `Vec`. That change is
orthogonal to correctness and can be made without altering the contract between
generated code and the runtime.

## Consequences

### Positive

- Correctness: a single path implements EVM expansion semantics.
- Safety: overflow and allocation failures are reported to generated code instead
  of causing UB.
- Simplicity: opcode emitters call one helper and branch on its result.

### Negative

- Performance: every memory touching opcode pays a runtime call. Inlining or
  special casing small fixed offsets could be explored later.
- Fragmentation: reallocation copies the whole buffer each time memory grows.
  This is acceptable for typical contracts but may matter for pathological cases.

### Future Work

- Over-allocate and track capacity separately from accessible length to reduce
  reallocation frequency.
- Add a small buffer optimization inside `Context` for contracts that use only a
  few words of memory.
