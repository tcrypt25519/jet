# ADR 002: Pointer-Based Memory Representation in exec_ctx

```
status: accepted
project: jet
area:
  - runtime
  - memory-model
```

## Context

During development, we discovered critical memory layout mismatches between three definitions of the `exec_ctx` structure:

1. Rust `Context` struct (`crates/jet_runtime/src/exec.rs`)
2. LLVM IR type definition (generated in `RuntimeBuilder`)
3. Historical handwritten IR (`runtime-ir/jet.ll`)

These mismatches caused:
- Struct size inconsistencies (32KB vs 65KB)
- Field offset corruption
- Potential memory corruption at runtime

The primary issue was the memory field representation:
- Rust used inline array: `memory: [u8; 32768]`
- Some definitions used nested struct: `{ptr, len, cap}`
- Different representations led to incompatible layouts

## Decision

We will use **pointer-based memory representation** with individual fields for all `exec_ctx` definitions:

```rust
struct exec_ctx {
    stack_ptr: i32,
    jump_ptr: i32,
    return_offset: i32,
    return_length: i32,
    sub_call: ptr,
    stack: [1024 x i256],
    memory_ptr: ptr,      // Heap-allocated buffer
    memory_len: i32,      // Current usage
    memory_cap: i32,      // Allocated capacity
}
```

## Rationale

### Why Pointer-Based Over Inline Array

1. **Flexibility**: EVM memory can grow dynamically during execution. Inline arrays with fixed size are fundamentally incompatible with this requirement.

2. **Size Efficiency**: Most contracts use far less than 32KB of memory. Pointer-based allocation only uses what's needed.

3. **Layout Consistency**: The `{ptr, len, cap}` pattern is well-established (like Rust's `Vec`) and easier to maintain consistently across multiple representations.

4. **EVM Alignment**: The EVM specification allows memory to grow unbounded (with gas costs). A fixed-size inline array doesn't match this model.

5. **Predictable Offsets**: Pointer-based representation makes field offsets predictable and consistent across Rust and LLVM IR definitions.

### Why Individual Fields Over Nested Struct

Originally considered:
```rust
mem: {ptr, len, cap}  // Nested struct
```

Rejected because:
- Adds unnecessary nesting level
- Complicates GEP (GetElementPtr) operations
- Makes field access less straightforward
- No semantic benefit over flat structure

## Implementation

### Rust Context
```rust
#[repr(C)]
pub struct Context {
    // ... other fields ...
    memory_ptr: *mut u8,
    memory_len: u32,
    memory_cap: u32,
}

impl Context {
    pub fn new() -> Self {
        let memory_size = (WORD_SIZE_BYTES * MEMORY_INITIAL_SIZE_WORDS) as usize;
        let memory_layout = Layout::from_size_align(memory_size, 32)?;
        let memory_ptr = unsafe { alloc_zeroed(memory_layout) };
        // ...
    }
}

impl Drop for Context {
    fn drop(&mut self) {
        // Deallocate memory buffer
        unsafe { dealloc(self.memory_ptr, memory_layout) };
    }
}
```

### LLVM IR Type (Generated)
```rust
let exec_ctx = context.struct_type(
    &[
        stack_ptr.into(),
        jump_ptr.into(),
        return_offset.into(),
        return_length.into(),
        sub_call.into(),
        stack.into(),
        mem_ptr.into(),   // Individual pointer field
        mem_len.into(),   // Individual length field
        mem_cap.into(),   // Individual capacity field
    ],
    PACK_STRUCTS,
);
```

## Consequences

### Positive

- **Correctness**: Eliminates memory layout mismatches and potential corruption
- **Flexibility**: Supports dynamic memory growth as per EVM semantics
- **Efficiency**: Only allocates memory as needed
- **Maintainability**: Single source of truth for type definitions via `jet_ir::Types`
- **Consistency**: Same representation across all layers (Rust, generated IR)

### Negative

- **Complexity**: Requires manual memory management in Rust (alloc/dealloc)
- **Indirection**: Extra pointer dereference on every memory access
- **Heap Allocation**: Two separate allocations (Context + memory buffer)

### Mitigations

1. Memory management encapsulated in `Context::new()` and `Drop` implementation
2. Pointer indirection is unavoidable for dynamic growth
3. Dual allocation is acceptable given the flexibility benefits

## Future Considerations

### Small Buffer Optimization (SBO)

Could add inline buffer for common small allocations:
```rust
const INLINE_MEMORY_SIZE: usize = 256;

struct Context {
    memory_inline: [u8; INLINE_MEMORY_SIZE],
    memory_ptr: *mut u8,
    memory_uses_inline: bool,
    // ...
}
```

Benefits:
- No heap allocation for tiny contracts
- Better cache locality
- Minimal complexity increase

Trade-offs:
- Increases struct size by 256 bytes
- Adds conditional logic to memory access

**Decision**: Defer SBO until profiling shows benefit.

### Memory Growth Strategy

Document and implement consistent growth strategy (e.g., double capacity when growing), similar to `Vec`.
