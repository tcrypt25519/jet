# ADR 006: Type-Level Enforcement of Memory Expansion in the Builder

```
status: accepted
project: jet
area:
  - compiler
  - memory-model
  - llvm/ir
```

## Context

ADR 005 defines the runtime mechanism for EVM memory expansion, but it does
not prevent an opcode emitter from accidentally reading or writing memory
without calling `jet_mem_expand` first. Generated code passes raw `i32` offsets to
runtime helpers, so the compiler can construct a memory access without any proof
that the range has been expanded.

The desired invariant is: every EVM operation that reads or writes memory must
expand the touched range before the access. This should be enforced by the
builder API rather than by convention.

## Decision

Introduce a private `MemoryRegion<'ctx>` type in the opcode builder. A
`MemoryRegion` can only be constructed by `expand_memory_region`, which calls
`jet_mem_expand` and returns the validated `(offset, size)` pair. All memory
access helpers in `ops.rs` accept `&MemoryRegion` instead of raw offsets.

```rust
#[derive(Copy, Clone)]
struct MemoryRegion<'ctx> {
    offset: IntValue<'ctx>,
    size:   IntValue<'ctx>,
}

fn expand_memory_region<'ctx, S: StackBackend<'ctx>>(
    bctx: &BuildCtx<'ctx, '_, S>,
    offset: IntValue<'ctx>,
    size: IntValue<'ctx>,
    label: &str,
) -> Result<MemoryRegion<'ctx>, Error> {
    call_mem_expand_checked(bctx, offset, size, label)?;
    Ok(MemoryRegion { offset, size })
}
```

`call_mem_expand_checked` emits a call to `jet_mem_expand`, branches to
`ReturnCode::Invalid` if it fails, and leaves the builder positioned at the
success block. A `MemoryRegion` therefore represents an LLVM value pair that has
survived the expansion check at the current insertion point.

Memory helpers such as `build_mem_load_value`, `build_mem_store_value`,
`build_mem_store_byte_value`, and higher level callers like `KECCAK256`, `RETURN`,
`REVERT`, `RETURNDATACOPY`, and `CALL` must obtain a `MemoryRegion` before using
the offset.

## Rationale

### A Rust Type is the Right Boundary

The compiler is written in Rust, while generated code is LLVM IR. Runtime helpers
are C-ABI functions and cannot carry Rust proof objects. The only place where the
invariant can be enforced statically is inside the builder itself, where memory
offsets are still Rust values.

### Raw Offsets Cannot Bypass Expansion

Changing the memory helpers to take `&MemoryRegion` removes the ability to pass a
bare `IntValue` offset. An emitter that wants to read or write memory must first
call `expand_memory_region`. Forgetting the expansion becomes a compile-time
error.

### The C-ABI Boundary Still Needs a Contract

The generated IR passes the `offset` and `size` fields from a `MemoryRegion` to
runtime helpers such as `jet_ops_keccak256` and `jet_contract_call_return_data_copy`.
Those helpers trust that the caller has already expanded the destination. They
keep defensive checks (for example, refusing the copy if the destination is not
expanded), but the normal path relies on the builder invariant.

## Implementation

### Builder Helpers

```rust
fn build_mem_load_value<'ctx, S: StackBackend<'ctx>>(
    bctx: &BuildCtx<'ctx, '_, S>,
    region: &MemoryRegion<'ctx>,
) -> Result<IntValue<'ctx>, Error>;

fn build_mem_store_value<'ctx, S: StackBackend<'ctx>>(
    bctx: &BuildCtx<'ctx, '_, S>,
    region: &MemoryRegion<'ctx>,
    value: IntValue<'ctx>,
) -> Result<(), Error>;
```

`MLOAD`, `MSTORE`, `MSTORE8`, `KECCAK256`, `RETURN`, `REVERT`, `RETURNDATACOPY`,
and `CALL` all construct a `MemoryRegion` and pass it to the appropriate helper
or runtime function.

### Call Output Buffers

`CALL` expands its output memory range before invoking the runtime. The runtime
`return_data_copy_impl` helper then copies return data into that range without
expanding it again. This keeps the output write under the same type-level rule
as every other memory write.

### Return Data Copying

`RETURNDATACOPY` expands the destination range in generated code before calling
`jet_contract_call_return_data_copy`. The runtime helper checks that the
destination is covered by `memory_len` and returns an error if it is not, but the
builder-level `MemoryRegion` is the primary guarantee.

## Consequences

### Positive

- Correctness: a missing `jet_mem_expand` call is caught when the compiler is
  built, not by a runtime test.
- Auditability: every memory access path is visually paired with an expansion
  call.
- Consistency: `CALL` output, return data copies, and ordinary `MSTORE` follow
  the same rule.

### Negative

- The invariant is scoped to `ops.rs`. Future helper functions must continue to
  take `MemoryRegion` rather than raw offsets, or the guarantee is lost.
- Runtime helpers that are called from outside generated code (for example, in
  unit tests) must still expand memory explicitly; the type cannot protect manual
  callers.

### Future Work

- Apply the same pattern to opcodes that are not yet implemented, such as
  `CODECOPY`, `CALLDATACOPY`, `LOG0` through `LOG4`, `CREATE`, and `CREATE2`.
- Consider whether runtime helpers should consume a thin wrapper or documented
  precondition so the contract is explicit at the ABI boundary.
