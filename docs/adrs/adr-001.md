# ADR 001: EVM Word Representation and Runtime Implementation Strategy

```
status: accepted
project: jet
area:
  - runtime
  - llvm/ir
```

## Context

We are building an EVM-to-LLVM JIT compiler. A critical design requirement is the accurate and performant representation of the EVM "Word" (a 256-bit integer). The EVM relies heavily on modulo arithmetic, bitwise operations, and overflow behavior specific to 256-bit types.

While LLVM IR supports arbitrary bit-width integers (e.g., `i256`), our host language (Rust) only supports native integers up to `u128`. This created a dilemma regarding how to define the runtime data structures and arithmetic:

- Should we emulate 256-bit words in Rust using arrays/limbs (e.g., `[u64; 4]`)?
- Should we write the runtime in Rust and compile it to IR?
- Should we continue handwriting LLVM IR?

We need a solution that maximizes runtime performance, ensures correctness (validating the IR), and improves maintainability over raw text-based IR files.

## Decision

We will represent EVM Words strictly as `i256` types in LLVM IR and implement the runtime using Rust as a typed IR construction DSL.

This implies a separation of concerns:

- **Data Plane (LLVM IR):** The actual runtime execution will use native `i256` LLVM values. We trust the LLVM backend to lower `i256` operations into optimal machine code (e.g., `addq`/`adcq` chains on x86_64).
- **Control Plane (Rust):** We will not compile Rust logic to IR. Instead, we will write Rust code that programmatically generates the LLVM IR. Rust acts as a meta-language to validate invariants (stack depth, type safety) at compile-time before the JIT ever executes.

## Detailed Design

- **Type Representation:** The runtime will treat EVM values as opaque handles (`i256` in IR). We will not cast them to `[u8; 32]` or `[u64; 4]` except at ABI/storage boundaries.
- **Runtime Functions:** Runtime helpers (e.g., `evm_mload`, `evm_add`) will be defined via Rust functions that emit LLVM `define` blocks. These are generated once per module and called by the JIT.
- **Safety Layer:** We will wrap raw LLVM builder calls in typed Rust structures (e.g., `struct EvmWord<'ctx>(IntValue<'ctx>)`) to prevent invalid IR construction (such as adding a pointer to an integer or stack underflows) via the Rust type system.

## Consequences

### Positive

- **Performance:** LLVM's optimizer canonicalizes `i256` better than hand-rolled limb arithmetic, enabling better vectorization and instruction scheduling per target architecture.
- **Correctness:** By using Rust as a construction DSL, we can enforce EVM invariants (stack bounds, operand types) at build time. Invalid IR becomes a Rust compilation error.
- **Maintainability:** Removes the brittleness of handwritten LLVM IR and the ambiguity of compiling Rust logic (which creates standard library dependencies and ABI mismatches).
- **Semantics:** Provides an exact semantic match to the EVM spec without emulation overhead.

### Negative

- **Ergonomics:** We cannot use standard Rust arithmetic operators (e.g., `a + b`) in the runtime code. We must use builder methods (e.g., `builder.build_int_add(a, b)`).
- **Complexity:** Requires the initial overhead of creating the "Typed DSL" wrappers around the LLVM builder/Inkwell to enforce safety.

## Alternatives Considered

### 1. Limb-based Emulation (`[u64; 4]` or `[u8; 32]`)

Rejected: Requires reimplementing complex big-int arithmetic in software. LLVM often fails to vectorize these loops efficiently, and it obscures the intent from the optimizer.

### 2. Writing Runtime in Pure Rust (Compiling Rust to IR)

Rejected: Rust lacks a native `u256` type. Using a library for `u256` results in suboptimal IR generation compared to native LLVM `i256`. Additionally, `rustc` may insert panic handlers or unwinding logic that is undesirable in a VM kernel.

### 3. Handwritten LLVM IR

Rejected: While performant, this approach lacks static analysis. It is easy to introduce subtle bugs (e.g., type mismatches, stack misalignments) that are only caught at runtime or by the LLVM verifier, rather than during development.
